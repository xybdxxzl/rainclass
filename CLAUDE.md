# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

雨课堂 (Rain Classroom) assistant — a PyQt5 desktop app that logs into yuketang.cn with a WeChat-QR-obtained `sessionid`, then monitors online lessons to auto-check-in, auto-answer problems, auto-send follow-along danmu, and voice-alert on calls/problems. All comments, UI strings, log messages, and commit messages are in Chinese; match that.

## Commands

```bash
pip install -r requirements.txt
python RainClassroomAssistant.py        # requires a Windows desktop session (Tk/Qt + pyttsx3 TTS)
```

There is no test suite, linter, or CI. Packaging is done locally with PyInstaller (`RainClassroomAssistant.spec` / `build.cmd`, both gitignored and not in the tree).

Runtime config lives outside the repo at `%APPDATA%\RainClassroomAssistant\config.json` (see `get_config_dir`/`get_config_path` in `Scripts/Utils.py`) — not `config.json` in the repo, which is gitignored anyway.

## Architecture

Entry `RainClassroomAssistant.py` → `UI/MainWindow.py:MainWindow_Ui` (a `QObject` wrapping a hand-tweaked pyuic5-generated UI). UI files carry "do not edit, regenerated by pyuic5" headers, but they *have* been substantially hand-edited (event wiring, `active()`/`show_login()` logic); the `.ui` sources are not in the repo, so treat the `.py` files as source of truth.

**Threading model — the single most important rule.** The Qt main thread owns all widgets. Worker threads (the monitor loop, one `Lesson` thread per course, answer threads, TTS threads) never touch widgets directly; they communicate only through the signals on `MainWindow_Ui`:

- `add_message_signal(str, int)` — log line + optional voice, `int` is the message type (see below)
- `add_course_signal(list, int)` / `del_course_signal(int)` — row add/remove in the 监听列表 table

`Lesson` receives these as `self.add_message = main_ui.add_message_signal.emit` etc. Any new UI-touching call from a worker must go through a signal. Shutdown works by `MainWindow_Ui.is_active` being polled by the monitor loop (which closes each `lesson.wsapp`); worker threads are `daemon=True`.

**Message type codes** (drive which voice alert fires, defined on `MainWindow_Ui.audio`): `1` danmu sent, `2` others' danmu, `3` problem received, `4` answer result, `5` I was called, `6` others called, `7` course lifecycle, `8` network up/down. `0` = log only, never spoken.

**Scripts/Monitor.py** — `monitor(main_ui)` loops every 30s calling `get_on_lesson`; for each lesson not already tracked it builds a `Lesson` and starts its thread. Handles network loss by polling `test_network()` and, on recovery, re-fetching. Duplicate detection relies on `Lesson.__eq__` comparing `lessonid`.

**Scripts/Classes.py** — `Lesson` is the per-course worker: `checkin_class()` (POST checkin, reads the `Set-Auth` response header into `Authorization`), then `wsapp.run_forever()` on `wss://www.yuketang.cn/wsapp/`. `on_message` dispatches on the `op` field: `hello` (backfill problems from the timeline via `get_problems`), `unlockproblem`/`presentationcreated`/`presentationupdated`, `probleminfo` (reply to our own probe, used when the app starts mid-lesson — filters out already-expired problems), `newdanmu`, `callpaused`, `lessonfinished`. `User` lazily fetches school number/name for danmu and call messages.

**Answer flow** (`Lesson.start_answer`) — all problems are answered by the LLM; there is no courseware answer matching. The ws `unlockproblem` push and the `probleminfo` reply are assumed to carry only `sid`/`problemid` + `limit`, **not** the problem text, so `_get_ppt`/`get_problems` are kept purely to cache problem *structure* into `self.problems_dict` (keyed by `problemId`) and `_extract_problem(data, problemid)` merges the ws payload over that cache. Gates, in order: no `problemid` → hint only; already in `answered_problem_ids` → ignore; cached `result is not None` (server says already answered) → ignore; `auto_answer` off or LLM disabled → hint only; `problemType` in `{None, 3, 5}` (unknown/vote/subjective) → hint only. Only a problem passing all gates is added to `answered_problem_ids` and dispatched to `Scripts/LLM.py` on a thread. The set is per-`Lesson`/per-run and needs no lock (`on_message` is a single ws thread); problems in a hint-only path are deliberately *not* recorded.

Because `ask_llm` takes seconds, `answer_questions` accepts an `elapsed` argument and subtracts the LLM round-trip from the `calculate_waittime` delay, so the total stays inside the problem's time limit. The `unlockproblem` and `probleminfo` branches both emit a type-0 `RAW <op>: <json>` log line unconditionally (not behind a flag) — this is the only way to confirm the real payload field names against a live lesson, since the push/reply shape is unverified.

**Scripts/LLM.py** — OpenAI-compatible `/chat/completions` client (any `base_url`; a trailing `/chat/completions` is stripped so users can paste a full endpoint), plain `requests`, temperature 0, asks for JSON back. Downloads problem images and inlines them as base64 data URLs (vision models; these downloads are not covered by the request `timeout`). Parses `{"choices": [...]}` / `{"blanks": [...]}`. Problem types: 1 单选, 2 多选, 4 填空; 3/5 unsupported and return `None`. HTTP/parse failures are raised as `RuntimeError` carrying the status code and response body so `_answer_by_llm` can log something actionable.

**HTTP conventions** — every `requests` call passes `proxies={"http": None, "https": None}` to bypass system proxies (the README warns users to disable proxies). Keep this when adding calls. `dict_result(text)` is the standard `json.loads`-to-dict wrapper used on every response.

**Config** — `get_initial_data()` in `Scripts/Utils.py` is the schema/source of truth; `MainWindow_Ui.check_config` creates the file if missing and merges in *any top-level keys* added since an older version (so new top-level config sections get picked up for existing users), but it does **not** fill nested keys — `UI/Config.py:load_config` compensates with `.get(key, get_initial_data()["llm_config"][key])` defaults. Each config group in `UI/Config.py` follows the same shape: a `QGroupBox` holding an enable checkbox plus a `when_<x>_on` child `QWidget` that is `setEnabled(False)` initially and toggled by an `enable_<x>_config` slot wired to `stateChanged` (so `setChecked` during `load_config` re-enables it). `llm_config` (`enabled`/`base_url`/`api_key`/`model`/`timeout`) has its own 大模型配置 group; `api_key` is stored in plaintext like `sessionid`. When adding a new group, follow that pattern and call its `enable_*` from `MainWindow_Ui.show_config` alongside the existing `enable_delay_custom()`/`enable_llm_config()` refreshes.
